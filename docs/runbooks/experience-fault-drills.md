# 体验服务故障演练（用户执行）

每条只注入一个明确目标，完成后恢复；不要对真实用户数据做破坏性步骤。
演练前记录控制库 schema 版本与发行 SHA。

## A1 隔离与直连

1. 用账号 A、B 分别登录，交换相册/资产/视频/事件/回合/作业/反馈 ID。
2. 直接访问 `http://127.0.0.1:8301/api/v1/assets/<B的资产>`（不带内部令牌）。
3. 直接输入 `/knowledge`、`/search`、`/settings` 等旧 URL。

期望：跨账号一律 404；禁用路由 403；内部端口无令牌 401；退出后旧 cookie 立即失效。

## A2 接收边界

在四个切点分别 `kill -9` 用户 API：写 staging、原子改名后、SQLite 提交前、返回响应前。
重启后观察：

- staging 残留按宽限期清理；
- 没有出现“已接收但没有作业”或“两个作业一份原件”；
- 同 `Idempotency-Key` 同文件重试返回原 `job_id/asset_id`；
- 上传 2 GiB 视频时进程 RSS 不随文件线性增长。

## A3 离线恢复与依赖等待

分别在观察、事件、向量、视频派生帧、事件总结、人物画像之后杀用户 API。
再分别停止 8100、8101、8103 数小时：

- 作业进入 `waiting_dependency`，不计阶段重试次数；
- 依赖恢复后自动续跑；
- 重跑不产生重复观察/事件/事实/向量；
- 坏文件只失败自身，作业显示 `partial` 或 `needs_attention`。

## A4 问答恢复

1. 流式回答中杀用户 API；浏览器保持页面。
2. 断开浏览器 SSE 后重连；重复提交同一幂等键；取消后重启；制造旧尝试晚到。

期望：同一问题、同一回合、一次最终回答；旧尝试不能覆盖终态；界面持续显示恢复/等待。

## A5 模型准入

两用户问答、一用户导入、同机 PhotoBench 评测同时请求：

- 模型并发不超过 `--parallel`（153 当前 2）；
- 问答优先，导入等待满 120 秒后按 4:1 放行；
- 旁路清单不为空时面板不得显示“优先级已生效”。

## A6 回忆与反馈

- 新账号 / 处理中 / 无合格事件 / 依赖恢复中四种首页原因不同；
- 所有视频点击前网络面板只有封面请求，点击后才请求原片并可拖动；
- 用户 API 与模型都停掉时仍能提交反馈；不附截图时控制库与文件目录都无图片副本。

## A7 监测与告警

分别停止用户 API、主模型、BGE、CLIP、控制面；制造配置漂移、GPU 传感器不可读、磁盘低于阈值。

期望：面板区分故障/缺测/过期，不显示假绿灯；真实 PID、构建 SHA 与端点可定位。

## A8 容量

按 1→3→5 名用户渐进开放，同时浏览/上传/问答并保留旧评测负载。
记录 RAM/swap、GPU 按 PID 显存、温度、磁盘、排队时长。出现 OOM、持续换页增长、
模型重启循环或旧服务明显退化即停在上一个规模。

## A9 备份与回滚

按 `experience-backup-restore.md` 备份并恢复一名用户；切换发行目录并回滚配置。
确认该用户可恢复、另一用户与旧 8191 不受影响、已接收原件不丢。
