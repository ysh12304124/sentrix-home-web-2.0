# 人物信息入库排查

2026-11-11，项目组决定问答查询暂缓（规划接地的改动单独放在 `wip/assistant-person-grounding`，
不合入），先保证人物的各种信息都能落库、查得到。本次逐条看了写人物信息的入口：

- 确认、改名、批量确认、预置、合并、别名；
- 家庭归属、家庭关系、画像；
- 导入时的人脸匹配，以及导入后的后处理。

再用真实库 `data/sentrix.db` 对已确认人物逐项核对覆盖率：提及、观察快照、外观证据、
事件参与者、人物瞬间、两套关系、归属与画像。

## 已修

### 1. 改名不同步照片上的人物快照

`SqliteEntityRepository.rename_person` 只更新 `entities`。`observations.people_json`
里存的是**名字**，它同时喂给好几处：
- 检索的人物条件和实体通道兜底（`name in observation.people`）；
- 记忆图的人物节点；
- 家庭图谱洞察的证据；
- 助手检索预览里的 `people`。

所以已确认的人一改名，他所有照片上记的仍是旧名，按新名字查不到。真实库眼下没有不一致：
库里仅有的 2 次改名都发生在确认之前，那时还没有快照。但只要先确认、再改名，就必然出错。

修复：
- 改名在同一个事务里把快照中这个 `entity_id` 的条目改成新名字。
- `_append_person_snapshot` 遇到已有条目时，把名字与状态对齐到当前实体，不再原样跳过。

### 2. 预置人物在样本照片上没有提及与快照

`SeedIdentity` 直接建出已确认的人、已确认的簇和人脸实例，但不写 `entity_mentions`，
也不写观察快照。在人物页确认簇（`ReviewCluster.confirm`）则会给每张脸写提及。

真实库里每个评测空间的 8 个预置人物，各有 1 张样本照片挂在已确认簇下却没有提及，
共 56 张。按实例预置（`face_instance_ids`）时样本就是相册里的照片，这个人在那张照片上
就查不到。

修复：
- 预置时给每个样本写提及，提及会连带写快照。
- `/people/seed` 路由随后刷新这些观察的事件参与者。

已有的 56 条评测数据没有回填。

## 没改，需要决定

- **导入后不给已确认的人补外观证据。** `ObserveAppearance` 只在确认和合并时调用，导入后处理
  （参与者 → 记忆图 → 事件总结 → 家族图 → 画像）里没有这一段。于是：
  - 先预置、后导入的人，外观证据为 0（真实库里所有评测空间都是 0）；
  - 确认之后才导入的新照片，也不会再补采。

  外观证据显示在实体详情页。要补的话，后处理需要对每个人、每个事件调一次视觉模型，导入时间会
  明显变长；而且 `ObserveAppearance` 现在每次都全量重采，要先改成只补缺失的部分。
- **按实例预置是复制实例，不是挪过来。** 原实例留在它原来的簇里（通常是一个待确认的人），
  同一张脸因此同时出现在两个人名下。这是数据重复，不是没落库；改成挪动会牵涉旧簇的原型和
  向量元数据，单独处理。
- **人物词法投影（`person_bridge`）确认后不刷新。** 已在 `claude/vibrant-meninsky-860194`
  分支修复（提交 `ac271bb0`，含回填脚本）。合入本分支后，人物合并改写快照的地方也要刷新投影。

## 核对过、没有问题的

- **关系**：通用 `relationships` 表由 PhotoBench 预置阶段批量导入，状态为待确认；家庭关系表
  由家族图推断和用户编辑写入。两张表分开是 1.0 的设计，前端读写的都是家庭关系表，两边一致。
- **快照完整性**：真实库 643 条快照条目里，没有悬空的 `entity_id`，没有名字或状态与实体
  不符的条目，已确认人物的提及也都写进了快照。
- **别名**：人物页走 `aliases` 属性。知识页写的 `alias` 只用于地点，两者不冲突。
- **`facts` 表**：0 行，以名字为键的事实眼下不会因改名或合并而丢失。
