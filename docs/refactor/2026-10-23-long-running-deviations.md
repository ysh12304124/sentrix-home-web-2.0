# PhotoBench 长期运行修复（本地，2026-10-23）

基线 `xy@94ce050`，开发分支 `codex/photobench-long-running`。本轮处理用户确认的六项缺陷与直接相关的历史加载减负；不修改模型、驱动和指标公式；按用户追加要求扩展产品导入观测协议，不操作远端。

- 普通 full/build/reuse 与 resume 共用 finally 收尾；终态执行体、线程注册释放，采样/落盘停止未确认时仍保留控制对象、阻止冲突和删除。取消不持注册表大锁等待 IO。
- 快照复制与所有共享 Judge 结果提交使用状态锁；Judge worker 使用独立 item，完成后主线程提交。落盘 IO 不持状态锁。请求序号仅成功后确认；等待提交和退出有共同期限，磁盘错误也发退出信号，停不下时显式 stop_pending。
- 终态对象缓存按文件修订失效，最多2项/64MiB，超大对象不缓存。全遥测投影最多2份、单份4MiB，key含状态与遥测文件版本；不改全有效样本统计后抽稀的规则。
- 增量接口 `include_history=false` 只读同次提交的 overview，含 item_count/effective summary 和240点实时窗口；普通 UI 轮询不读全遥测。旧默认 true 保留。全曲线显式按钮读取，记忆/关键帧分析在面板展开后才请求；切换请求/卸载可取消客户端请求且不误重试。取消浏览器请求不能证明服务端线程或产品操作退出。
  曲线卡片按既有 `history_mode` 明示窗口或全轮，分别展示绘图点数与整轮采样数；窗口横轴从窗口首点计时，不能标作完整测评过程。无范围的旧记录不推断为全轮；仅有阶段快照时用序号横轴并注明不代表真实耗时。仅修正展示来源说明，不改加载策略、采样、空值或指标统计。
- 新写入先完整写/fsync两份结果与轻元数据，再原子提交 generation 清单；恢复、索引、读侧按清单取相同版本。兼容根文件独立导出，提交后导出/清理失败有日志，权威版本不倒退。当前/上一检查点保留；清除的是滚动检查点及未提交临时文件，不是历史 run/原始遥测。旧目录首次读取只写可重建的瘦索引，原文不改；温启动不重复解析终态大轨迹。
- reviews/start/rejudge/config/prompt 等 async 路由完成收包后，把同步用例交给 Starlette 有界线程池；不扩大线程池，不改业务重试或状态码。

`run.json`/`results.jsonl` 内容形状仍兼容旧工具；在线一致读取以 `snapshot-commit.json` 为准。不能将根文件的两次替换当事务。目录租约仍只允许单实例，文件系统必须支持同目录原子 replace 与 fsync。提交点后根导出失败，应先停写再从清单选中的 generation 恢复两个导出，不能用旧根文件覆盖权威版本。

本轮不宣称消除任意时长/规模增长：单轮 sampler 全样本驻留与反复精确聚合、整份题目轨迹检查点重写、QA 真正存储分页、追加事实/流式导出、统一全进程退出、产品协作取消、超1000媒体分页仍是独立后续工作。首次旧历史索引构建仍要解析原文件一次。用户取消24小时专项，本轮用100轮合成执行、1000条历史、并发读写与写盘故障进行本地验证；正式真机与长任务验收留待设备可用，不能以本地 CI 替代。

补充：保存失败的当前进程诊断经瘦索引投影到详情，标明来源与旧检查点状态，避免因磁盘无法写入而显示“仍运行但实际已退出”；没有补写原始记录或伪造成功提交。前端接入后台scan状态，初扫未完成时继续取列表并推迟自动选中判断。双代快照及独立兼容导出需要额外磁盘，稳定态最多约为旧单检查点两文件占用的三倍（不含raw），写入时还需容纳一份暂存代；超大轨迹的存储拆分仍在后续范围，不宣称解决全部容量增长。


追加交付：保留同步导入POST，按可选operation_id查询通用进度。domain不可变ImportProgress/Store端口、application TrackImport、bootstrap注入有界内存适配器。实际扫描total（应用limit后）与已结算媒体计数分开，已结算=新增+去重+失败；预取阶段失败按有序提交位置结算，计数不倒退。总结、参与者、家庭图谱、人物画像均有独立步骤，媒体满计数仍为running，响应完成才completed；致命异常failed并保留已处理计数及最后步骤。单张媒体失败仍遵循原批量契约，不伪装成未捕获异常。

产品进度查询为async且在路由体直接取容器，不使用同步Depends或模型/数据库线程池；内存锁只覆盖常数规模操作。32活跃+128终态上限，重复在册ID409、容量429先于副作用。进程重启/终态淘汰404，无持久队列或跨worker恢复承诺；产品部署仍单worker。PB每秒查询一次、单次3秒超时，冻结的运行客户端供POST/GET共用。观察线程finally停止并核实，停不下则observer_stop_pending阻止后续冲突；未知POST结果不重放、不宣称产品已经取消。保存最后观测、后端步骤时间/查询时间、本地接收时间/查询故障及各目录最终观测；这是轮询检查点，不保证捕获每个短暂中间步骤。旧服务404或旧客户端缺可选能力时明确进度不可用。

前端显示当前目录媒体计数与进度条（不将目录数/manifest推测为媒体总数）、收尾步骤、更新时间和每秒墙钟；10秒未查询刷新明示上次观测，不将未变更步骤当作故障。普通轮询不打断手动全曲线读取；同提交版本保留已加载全曲线，检查点版本变化则恢复实时窗口，避免混版本聚合。

持久化补充：提交指针发布后，目录fsync失败仍向上报告持久性不确定，保留已选代供读取/恢复；兼容导出失败不能跳过滚动代清理，避免连续导出故障无界积累检查点。当前与上一代的空间代价仍适用。

CI暴露并确定性复现的既有SSE交接竞态：首次历史查询后任务恰好终态，旧路由直接返回complete，漏掉两次读取之间的新事件。现在终态与broker退出时按cursor补读持久事件再complete；关闭channel后订阅不再等待不会发生的下一次唤醒，结束时补发尚未交付的backlog。原事件顺序、去重、断线续传和“首条计划”断言保留，新增确定性竞态测试。只修复事件交付，不修改Agent决策、模型调用或质量规则。

导入终态scanned_count按产品完整结果计数确定，manifest总量仍保留为预期；缺完整事实不重算。保存失败的进程内诊断包含真实结束时间/原因，UI不会让已终止任务的旧running检查点继续累积墙钟。


### T006 Judge实时进度（2026-10-23）

QA阶段的规范进度存于`phases.qa_eval.progress`：`agent_completed`为已终态题数（含明确任务失败，不含scheduled/running），`completed`保留成功完成题数；`judge_completed`为已结束的Judge题数（含评分失败，不含跳过），`judge_total`为应评题数，`judge_skipped`单列。有效分数仍由统一评分规则统计为`summary.judge_valid_count`，合法0分有效，失败不补0。新执行在持锁检查点同步items和进度；阶段外层agent/judge计数保留兼容并与内层相同。未配置Judge时内层Judge计数为null、并发为0，前端显示未配置。

Agent和Judge仍使用独立线程池，协调器等待任一池完成即提交结果，不再等全部Agent结束才回收Judge。恢复运行从已有明确Judge终态初始化计数，跳过事实单列，不重新请求既有评分。Agent阶段墙钟在最后Agent结果返回时结束，不包含等待Judge尾部。前端阶段卡和列表共用同一读取函数，优先内层、缺失时兼容外层；没有记录显示?，不以0替代未知。历史原文不改写，旧运行自身未更新的计数仍属于旧检查点事实，不能据有效评分数补造完整Judge终态。

复现测试覆盖一题Agent阻塞时另一题Judge的合法0分、返回失败和抛异常及时可见；resume既有评分、失败/跳过、取消未开始题不假报完成、可空投影及历史外层字段UI。仅本地验证，未触碰四机或启动真实测评；后续发布按公共执行路径影响验证。
