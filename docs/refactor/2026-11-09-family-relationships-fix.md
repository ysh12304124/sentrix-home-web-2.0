# 人物关系创建与全部相册读取修复

人物页使用空 `scope_id` 查询全部相册。此前详情的对方列表包含其他空间的人物，
但关系写入明确要求两端属于请求中的同一个空间，导致界面允许选择、提交后才报 400。
此外，全部相册读取用空空间 ID 查询关系，已保存的同空间关系也无法返回给详情与图谱。

按用户确认保留空间隔离：详情只提供同空间的其他人物；跨空间或已失效的预选不能提交。
没有其他同空间人物时显示说明。后端原有空间校验、关系白名单、用户锁定、双向写入与
撤回规则保持不变，不合并空间、不迁移人物或历史关系。

`GET /api/v1/family-graph?scope_id=` 先按原有可见性规则读取人物，再按人物实际所属
空间去重读取有效关系，`scope_ids` 返回这些实际空间；指定空间与已合并图的读取保持原状。
接口字段与错误格式不变。隐藏空间的关系不会因全部相册查询而暴露。

回归验证：

- `apps/api/tests/contract/test_family_routes.py`：多个可见空间的关系读回、隐藏空间过滤、
  指定空间隔离与跨空间写入拒绝。
- `apps/web/src/features/people/family/PersonDetail.test.tsx`：同空间候选、写入空间与跨空间预选拦截。
- `apps/web/src/features/people/PeoplePage.family.test.tsx`：建关系后重拉，详情、关系计数与图谱同步显示。

不对真实数据库写入测试关系。已失败的创建没有落库，需要用户在修复后选择同空间人物重新建立。

验证结果：后端家庭路由与仓储 57 项、前端人物关系 29 项通过；前端 TypeScript、
lint 与生产构建通过，修改的 Python 文件 lint/格式检查通过。真实数据库只读备份上的
初次读取返回 5 个空间、95 个人物与 8 行有效关系；当时没有用户确认关系，保持图谱不展示推断边的规则。

全量 `make ci` 在其他文件既有的 35 个 lint 错误处中止；全量类型检查、架构与模块地图
也有未涉及文件的既有错误。前端全套测试有 34 项失败，在临时目录导出的未修改 HEAD
上复测同样为 34 项失败；本次人物关系用例均通过。没有为消除这些错误而扩大修复范围。

## 后续运行进程核验

用户重试后，数据库已存在 5 对有效的用户确认关系，但 Vite 仍返回空图。
核验发现旧启动脚本的后台 API 监听 `127.0.0.1:8191`，新 `make dev` API 监听
`0.0.0.0:8191`，本机两进程同时存在。Vite 代理目标是回环地址，因此仍命中修复前的进程。
同一次只读 HTTP 对比中，回环 API 与 Vite 返回 0 行关系，局域网 API 返回 18 行，
其中 10 行为用户确认的双向关系。

确认无进行中的导入、视频任务或问答后，优雅退出旧后台 API，保留新 API 与模型服务。
复核回环、局域网和 Vite 三个入口均返回 5 个空间、18 行有效关系及 10 行用户确认关系。
此处理没有新增、删除或重写关系。完整 Mac 脚本已经启动 API 时，不再另起 `make dev`；
需要切换 API 启动方式时，先退出已有 API，并核对实际监听进程。
